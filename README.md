# 念头盒 NianBox

> 把每一个念头，留给未来的创造。

念头盒（NianBox / Idea Inbox）是一个轻量的个人灵感捕捉工具。它要解决的不是「记笔记」，而是 `发现问题 → 随手记录 → 逐步整理 → 验证想法 → 转化为产品 → 发布作品` 这条链路中最容易断裂的第一步：**把念头先留下来**。

---

## 一、产品是什么

生活中经常冒出一些实际问题：停车场明明知道位置却总是找不到空位、社区旧书没有合适去处、某个重复操作想写个自动化工具。这些念头往往来自生活、工作、旅行或产品体验，但大部分因为没有及时记录就消失了；即便记下来，也散落在收藏夹、备忘录和各种聊天记录里。

念头盒希望成为一个长期积累创意的入口：

- **打开就能写**，不需要先想标题、选文件夹、挑分类。
- **不评价创意好坏**，不成熟的想法也值得保存。
- **不需要注册就能开始**：记录默认只存在本机浏览器（IndexedDB），离线也能写、能看、能导出。
- **云端是可选增强，不是前提**：登录后同一份念头能在手机、电脑与 PWA 之间同步；
  接口地址在构建时注入，没注入就完全不联网（见第九节）。
- **没有你的确认，内容不会被发出去**：AI 分类、AI 生图只在服务端进行，界面会写明数据发给谁；
  本机制作的卡片、作品图片都只留在本机，不自动上传、不自动公开。
- **公开的是应用本身，而不是你写的灵感**。

名字里的「盒」指的是那个随手放东西、以后要用时能找到的地方。列表在没有任何标题的时候，会用正文的第一句作为**显示标题**，但绝不会改写你输入的原文。

## 二、已经实现了哪些功能

### 1. 首页 · 随手记

- 首屏就是输入框，打开即可输入，不需要先跳转。
- 多行文本输入，支持手机原生键盘、粘贴、长文本。
- 分类是可跳过选项：生活问题 / App·产品创意 / Skill·自动化 / 网站·小程序 / 其他，默认不选。
- 主要按钮「记下这个念头」，保存成功后提示「收好了，这个念头不会轻易丢失。」。
- **只有数据库真的写入成功才会提示成功**；写入失败会保留输入内容并给出真实错误。
- 内容为空时不会创建记录，提示「先写下一句话，再收进念头盒。」。
- 未保存内容会留一份本地草稿，刷新后可一键恢复或丢弃（正常保存不会弹出任何打扰性确认框）。
- 保存后清空输入、更新记录总数、把新内容放进「最近的念头」。

### 2. 念头收件箱

- 集中展示全部念头，默认按最近更新时间倒序（同时保留创建时间，编辑不会丢失原始创建时间）。
- 每条展示正文摘要、创建时间、分类、当前状态、置顶标记，以及可选的来源项目名。
- 支持关键词搜索（正文、标题、备注、标签，英文不区分大小写）、分类筛选（含「未分类」）、状态筛选、只看置顶；多个条件可叠加。
- 支持置顶 / 取消置顶、编辑、删除、进入完整详情。
- 删除前必须确认；删除是软删除，会进入回收站。
- 空状态友好引导：「这里还没有念头。留意生活中的小问题，它们可能是下一个作品的起点。」；搜索无结果时提示「没有找到匹配的念头。」。

### 3. 念头详情与编辑

- 默认只显示最必要的字段，其余字段收在「完善这个念头」可展开区域中。
- 字段：标题（可选）、正文（必填，原样保留）、分类、状态、标签（多个）、置顶、备注/补充思考、解决的问题、目标用户、潜在产品形态（App / 网站 / 小程序 / Skill / 其他）、项目链接（GitHub 仓库、已发布网页等 URL）。
- 状态固定六种：待整理、值得研究、准备开发、开发中、已完成、暂缓；默认「待整理」。
- 编辑真正写入 IndexedDB，刷新后保留；编辑不会改变记录 ID 与创建时间。
- 长文本、特殊字符、中文、Emoji 与 URL 均按原文处理。

### 4. 创意项目库

- 可以把一条念头「升级为创意项目」，升级后保留指向原始念头的链接。
- 「可以升级的念头」列出所有还没升级成项目的念头（含刚记下的「待整理」），可一键升级；
  已标记「准备开发 / 开发中」的排在最前，不会打乱既有推进节奏。
- 项目字段：项目名称、需要解决的问题、目标用户、核心功能、产品形态、当前进度、GitHub 仓库 URL、已发布网址。
- 进度：准备中、开发中、打磨中、已发布、暂缓。
- 念头状态会随升级推进到「准备开发」，并记录来源项目；项目详情页可一键跳回原始念头。
- 第一版**不做**看板协作、工时管理、团队账号等复杂功能。

### 5. 回收站

- 软删除的念头与项目集中在这里，可恢复或永久删除。
- 永久删除念头时，会一并处理其关联项目，不留悬空引用。

### 6. 设置与数据

- 本地存储说明、当前数据统计（念头数、项目数、置顶数、回收站记录数）。
- 一键导出 JSON 备份、导入 JSON 备份、清空全部本地数据（需二次确认）。
- 意见反馈入口、匿名使用统计开关（含设备标识重置）、开发者看板入口（仅构建时开启时才显示）。
- 隐私说明：念头默认只保存在这台设备上，不登录也能完整使用；匿名统计上报的只有白名单里的枚举值，
  可一键关闭；AI 分类与生图只在你主动点击后才把内容发到服务端（页面上会写明发给谁）；
  作品图片只留在本机，不进入云端同步、不自动公开。

### 7. PWA 与离线

- Web App Manifest（名称、短名称、主题色、192/512 图标、maskable 图标）与 Service Worker。
- 静态资源预缓存 + 导航请求网络优先：**在线时总能拿到最新版本**，离线时已缓存界面仍能打开，本地数据依然可读可编辑。
- 导航请求显式使用 `cache: 'no-cache'`（条件请求，命中 ETag 时返回 304），因此**新版本发布后，用户下一次刷新就能看到，不用等浏览器 HTTP 缓存自然过期**，也不需要手动清缓存。
- `public/sw.js` 里的 `CACHE_VERSION` 是离线缓存的版本号：改动缓存逻辑、或需要让所有用户强制换新时把它加一，旧缓存会在 `activate` 阶段自动清理。
- Service Worker 只在生产构建中注册，开发环境保持干净；注册失败不影响应用启动。

### 8. 意见反馈与匿名使用统计（开发者可见的运营数据）

这一节回答「开发者怎么知道用户在用、卡在哪里，用户又怎么把问题告诉开发者」。
设计上有一条硬规则：**内容留在本机，运营数据只有事件名与枚举值**。

- **意见反馈**（`#/feedback`）：类型（遇到问题 / 功能建议 / 使用感受 / 其他）+ 正文 + 可选联系方式 +
  可选诊断信息（默认**不勾选**，且只有应用版本、平台、界面语言、念头与项目的**条数**）。
  提交先写入本机 IndexedDB，再尝试上报；上报失败标为「暂未发送」，下次打开应用自动补发，不会丢。
  本机留存的反馈在反馈页完全可见，可逐条删除。
- **匿名使用统计**：事件名只有一份白名单（`src/services/analytics.ts` 的 `EVENT_NAMES`），
  参数只有 `source / status / progress / bucket / kind / result / state` 这些**枚举值**，
  由 `sanitizeProps()` 按白名单过滤——调用方即使误传 `{ content: idea.content }`，
  内容也不会离开设备。数量按档位上报（`1 / 2-5 / 6-20 / 21-100 / 100+`），不报精确条数。
  只有一个随机生成、可随时重置的设备标识；没有 Cookie、不记录 IP、不做指纹。
- **开关与边界**：设置页可一键关闭统计；关闭立即停止上报并**清空待发送队列**，
  关闭动作本身不上报（只有开启动作会留一条记录）。事件先入本机队列，批量上报，断网时下次自动补发，
  任何网络失败都被静默吞掉，绝不会影响记录念头。
- **开发者看板**（`#/dev`）：显示本机的采集状态、最近 14 天活跃度、事件明细、本机反馈记录，
  并可导出 JSON。入口默认关闭，构建时注入 `DEV_DASHBOARD=1` 才出现。
  **这一页读不到其他用户的数据**——它只有本机自己的数据。
- **跨用户的运营数据**在后端：应用只带「只能写入」的令牌，读取凭据永不进前端产物，
  因此别人拿到网址也读不到数据。怎么接入、用哪些查询做运营决策，见交付文档
  《运营数据与用户反馈-接入指南》。

### 9. 云端账号与跨终端同步（可选）

这一节能回答「我在电脑上记的念头，手机上为什么看不到」。答案取决于**这次构建有没有注入云端地址**：

- **没有注入 `VITE_CLOUD_ENDPOINT`**：应用是纯本地的，一个网络请求都不发。云端相关的页面会如实显示
  「这个构建没有配置云端地址」，并给出接入方式。此时换设备只能靠「导出 → 传输 → 导入」。
- **注入了云端地址**（本仓库的线上构建就是这种）：`#/cloud` 页可以注册 / 登录，登录后同一账户在
  桌面浏览器、iOS Safari、PWA 和微信内置浏览器里读到的是**同一份**念头与项目。

同步的工作方式（不是「把本地库整个传上去」）：

- 本地 IndexedDB 始终是**写入的第一站**：先写本机、界面立刻反馈，再把变更放进 `outbox` 队列推送。
  因此断网、服务端挂掉、令牌过期都不会让你丢掉刚写下的内容——记录还在本机，等恢复后再补发。
- 服务端（Cloudflare Workers + D1）**逐条校验归属**：每条记录都带用户 ID，查询与写入都按
  当前登录用户过滤，他人无法读到你的数据（`server/cloud-worker.test.mjs` 里有对应的拒绝用例）。
- 新增、编辑、搜索、分类、置顶、删除、恢复、项目升级这些操作都走同一份数据；
  收件箱里会区分「已同步」与「只在本机」的状态，不会把没同步的记录说成已备份。
- 保存失败时**保留输入并如实报错**，不会出现「看着成功了、其实什么都没存」。
- 旧数据迁移：先在设置页「导出数据」拿到 JSON 备份，登录后导入即可；导入按 ID 去重，不会清空现有数据。
- 密码找回依赖服务端邮件服务；邮件服务没配置时，`#/cloud` 页不会出现「已发送邮件」这种说法。

### 10. 灵感海报：AI 生图与本机卡片是两种能力

「把这个念头变成图片」这条路径上有两个入口，**它们刻意不是同一件事**：

| | 本机制作的念头卡片 | AI 增强生图（灵感海报） |
| --- | --- | --- |
| 需要登录 | 不需要 | 需要（内容要发到服务端才会处理） |
| 需要网络 | 不需要，纯本机 Canvas 绘制 | 需要，服务端调用图像模型 |
| 图上内容 | 你确认过的念头文字（原文/标题可选） | 抽象后的主题词与视觉元素，**不含原文** |
| 消耗额度 | 不消耗 | 消耗服务端模型额度 |
| 界面标注 | 「本机制作的念头卡片」「本机绘制，不是 AI 生成」 | 「AI 灵感海报」（仅在服务端真的返回图片时） |

- 未登录、或服务端没有配置图像服务时，页面**不会挡在登录页**，而是直接给你本机卡片这条路，
  并明确写出「这不是 AI 绘图，也不会消耗任何模型额度」。
- 本机卡片复用应用既有的品牌设计（`BrandMark`、`BRAND_STAR_PATH` 与品牌 CSS 变量），
  支持 3:4 竖版与 1:1 方形，可保存图片、可复制文字、可用系统分享。
- 分享前会把「将要出现在图上的文字」逐字列出来让你确认；提交给图像模型的是抽象结果，
  抽象失败或隐私检查不通过时**停止生成**，不会用假图片顶替。
- 服务端在运行期会通过 `GET /capabilities` 回显 `classify` / `abstract` / `image` / `mail`
  是否真的可用，界面按它显示真实状态，不靠前端猜测。

### 11. 我的作品（本机作品库）

- 生成结果可以「保存到我的作品」；保存成功才提示成功，写不进去就如实报错并保留刚画好的图。
- 作品**元数据与图片分开存**：`works` 表存作品 ID、关联念头、类型、生成方式（AI / 本机）、
  风格、比例、标题与创建时间；`workImages` 表存图片本体。列表页只读元数据，不会把几 MB 图片读进内存。
- 作品**只在本机**：不进云端同步、不上传、不自动公开（`saveWork()` 不调用同步队列）。
  换设备看不到，属预期行为。
- 作品可以预览、下载、系统分享、再创作一张，也可以删除；删除前必须确认，删除时元数据与图片同事务删掉。
- 关联的念头被**永久删除**时，作品与图片一起清理，不留悬空数据；念头只是进回收站时作品先收起来，
  恢复念头后又能看到。
- 首页有「最近作品」区块（空态是「去做第一张卡片」），并提供「查看全部」进入 `#/works`。
  它不在底部导航里额外占标签，导航仍是五个。
- **图片按需读取**：`readWorkImages(ids)` 只按给定 ID **逐条** `get`，不再把整个 `workImages` 表
  读进内存；首页只预读最近 **4** 件作品的图片，作品页先读轻量元数据、可见缩略图才加载，
  打开预览 / 下载 / 分享前再确保取到对应原图，并有一层小容量内存缓存，来回切换不会重复读同一批图。
  图片读不到会如实提示（例如「图片数据缺失」），不会拿空白图或假缩略图掩盖错误。
- **作品纳入备份**：导出的 JSON 备份（格式版本 **v2**）除念头与项目外，还包括作品元数据、
  **图片数据本体**以及作品与念头的关联；回收站中尚未永久删除的念头及对应作品也会一起导出。
  图片仍然只存在本机与这份备份文件里，**不会因为导出 / 导入而上传到云端**。

### 12. AI 自动分类

- 保存念头**先落库**，再异步请求服务端 `/ai/classify`。分类失败不影响保存，念头依然是完整的。
- 分类结果可被用户手动改；也可以重新分类。模型与密钥只存在服务端（Worker Secret），前端产物里没有。
- 服务端未配置模型时，界面不会显示「已自动分类」，而是留给你自己选。

### 13. 邮件发送与 AI 工具流转

- 收件箱支持多选 / 全选 / 取消选择，批量操作：**发送邮件、交给 AI、生成海报**。
- 邮件会自动整理主题与正文（**正文用你保存的原文，不做摘要改写**），发送前可预览、可修改。
- **是否真的发出去了，取决于服务端是否配置了邮件服务**：配置了就走服务端发送，并以服务端返回的
  `sent: true` 为准；没配置就退化为 `mailto:` 预填到你自己的邮件应用，界面写的是「请在那里确认后发送」，
  绝不把「预填」说成「已发送」。发信永不自动重试，避免重复发出。
- 「交给 AI」提供 ChatGPT / WorkBuddy / 豆包 / 通义千问 / 智谱 GLM 的适配器与任务模板
  （问题分析 / App 方案 / Skill 开发 / 网站开发 / 可行性评估 / 自定义）：能直接打开的就打开，
  不支持的平台给出**可编辑提示词 + 复制 + 系统分享**，不伪造「已自动发送」。

## 三、技术栈

| 方面 | 选择 |
| --- | --- |
| 界面 | React 19 + TypeScript（`strict`，开启 `noUnusedLocals` / `noUnusedParameters`） |
| 构建 | Vite 8（rolldown） |
| 样式 | 单一设计系统 `src/styles/global.css`：第 1 层 `--color-*` 是 NianBox 品牌色表（与官网同一套固定色值），第 2 层 `--nb-*` 是按用途命名的语义别名，组件只引用第 2 层；圆角、间距、字体、按钮高度同样由变量统一 |
| 数据 | IndexedDB（浏览器原生），封装在 `src/services/` 中，界面与数据模型分离 |
| 路由 | 哈希路由（`#/inbox` 这类地址），部署在静态托管的子路径下刷新不会 404 |
| PWA | 手写 Manifest 与 Service Worker，无第三方 PWA 插件 |
| 云端同步 | 自建后端（可选）：Cloudflare Workers + D1，构建时注入 `VITE_CLOUD_ENDPOINT`；未注入时应用是纯本地的 |
| AI 能力 | 只经服务端调用（分类 / 抽象 / 生图），密钥存在 Worker Secret 里，前端产物中没有任何模型密钥 |
| 运营数据 | 自建后端（可选）：构建时注入接口地址与**只能写入**的令牌；未配置时不发送统计请求 |
| 测试 | Vitest 5 + @testing-library/react + jsdom + fake-indexeddb |
| 部署 | GitHub Actions + GitHub Pages（官方 Pages 发布方式） |

前端运行时依赖只有 `react` 与 `react-dom`，**没有引入任何浏览器端的第三方服务 SDK**。
云端账号、AI 分类与生图、运营统计都是**可选的服务端能力**，靠构建时注入的地址开关：

- 不注入 `VITE_CLOUD_ENDPOINT`：应用是纯本地的，不发送业务网络请求，换设备只能靠导出 / 导入；
- 注入了云端地址（本仓库线上构建就是这种）：账号登录后同一账户跨终端读写同一份数据，
  AI 分类 / 抽象 / 生图走服务端代理，模型密钥只存在 Worker Secret；

### 环境要求

- **pnpm 11**（`package.json` 的 `packageManager`/`engines` 按此约束；使用 npm/yarn 也可以，但锁文件是 `pnpm-lock.yaml`）

### 安装与启动

```bash

pnpm dev
```

开发服务器默认监听 `http://localhost:5173/`，默认 Base 路径为 `/`，刷新任意哈希路由都不会 404。

### 关于 `--configLoader native`

`package.json` 中的脚本都带了 `--configLoader native`（Vite 官方 CLI 选项，官方标注为 experimental）。原因：

> Vite 8 默认会用 rolldown **打包**配置文件（`vite.config.ts`），而这条路径在 Windows 上会调用一次 `exec("net use")` 来探测网络驱动器映射。在禁止派生进程的环境里，这一步会抛出 `spawn EPERM` 导致构建/测试无法启动。改用 `native` 后由 Node 原生加载配置文件，绕开这一步，行为与 `bundle` 一致。

本地 macOS / Linux / 普通 Windows 环境**去掉这个参数也能正常工作**；保留它是为了让脚本在受限环境中同样可运行。原生加载 `.ts` 配置文件依赖 Node 的类型剥离能力，这也是 Node 版本要求 ≥ 22.18 的原因。如果你的环境低于该版本，把脚本里的 `--configLoader native` 去掉即可。

### 品牌设计系统守护测试

`src/test/brandTokens.test.ts` 把《NianBox 品牌视觉系统统一规范》里的硬性规则变成可执行的断言，因此新增页面时如果写错了颜色，`pnpm test`（以及 CI）会直接失败：

- **颜色只能写在一处**：所有色值必须出现在 `global.css` 的 `:root` 里，组件层只允许写 `var(--nb-*)`；组件层出现 `#` 开头的 hex、数字型 `rgb()` / `rgba()` 或 `color-mix()` 都会失败；
- **品牌固定色值不许漂移**：`--color-brand` 等 14 个色值与规范逐字比对（例如 `--color-brand` 必须是 `#7759dd`）；
- **品牌图形不许用字符代替**：`✳`(U+2733)、`✱`(U+2731)、`✦`(U+2726) 这类字符在 iOS Safari 与微信内置浏览器里会落到系统 Emoji 字体上（甚至显示成绿色「米字」），所以源码、`index.html`、`favicon.svg`、`manifest.webmanifest` 里都不允许出现，品牌星形只能走内联 SVG（`src/components/BrandMark.tsx`）。

新增颜色时的正确做法是：先在 `:root` 第 1 层加一个 `--color-*`（或在品牌色表里挑最接近的一个），再在第 2 层加一个按用途命名的 `--nb-*`，组件里只写 `var(--nb-*)`。**不要**在组件里另造一个相近色。

## 七、GitHub Pages 部署方法

仓库中已包含 `.github/workflows/deploy.yml`，流程为：

1. 检出代码（`actions/checkout`）；
2. 安装 pnpm 与 Node 24（`pnpm/action-setup` + `actions/setup-node`，启用 pnpm 缓存）；
3. 安装依赖（`pnpm install --frozen-lockfile`）；
4. 类型检查（`pnpm typecheck`）；
5. 运行自动化测试（`pnpm test`）；
6. 生产构建（`pnpm build`，注入 `BASE_PATH=/${{ github.event.repository.name }}/` 与 `VITE_OFFICIAL_SITE_URL`，后者的默认值与覆盖方式见第 10.2 节）；
7. 校验构建产物里确实带有官网地址（在 `dist/assets` 里 `grep` 一下）：不通过只打一条 `::warning::`，**不会**阻断发布——因为这个入口是可选的；
8. 配置 Pages（`actions/configure-pages`）→ 上传产物（`actions/upload-pages-artifact`，路径 `dist`）→ 发布（`actions/deploy-pages`）。

**第 4、5、6 步任意一步失败，构建任务即失败，部署任务不会执行**，因此不会把构建失败的版本发布出去。

工作流使用官方 Pages 发布方式（OIDC + `pages: write` / `id-token: write`），**不需要在仓库里配置任何令牌或密钥**。

触发条件：推送到 `main` 分支，或在仓库的 Actions 页面手动触发（`workflow_dispatch`）。

> **如果应用与官网在同一个仓库**（官网占站点根目录、应用源码放在 `app/` 子目录），请改用交付物 `deploy.yml` 替换本文件：它会在一次运行里先构建应用（注入 `BASE_PATH` 与 `VITE_OFFICIAL_SITE_URL`），再把官网文件与应用产物组装成同一个站点发布，从而同时上线官网（`/`）与应用（`/app/`）。上面这份单应用工作流适用于**应用单独占用一个仓库**的情况。两种形态的取舍见第十节。

## 十、与官网（落地页）对接

念头盒有相互独立的两部分，既可以各自部署，也可以放在同一个站点的不同子路径下：

- **官网（落地页）**：介绍产品理念的静态页面，位于站点根目录（`index.html` / `styles.css` / `script.js` / `app-config.js`）。
- **应用（本体）**：本仓库这部分代码，构建产物 `dist/`，部署在 `/app/` 子路径下。

两边只通过**一条约定**对接，并且**地址都不写死在源码里**。

### 1. 官网 → 应用：`app-config.js`

官网根目录的 `app-config.js` 暴露一个冻结对象：

```js
window.NIANBOX_CONFIG = Object.freeze({
  appUrl: "https://<你的用户名>.github.io/niantou-box/app/",
  appLabel: "打开念头盒 ↗",
  appStatus: "live" // 应用真正可访问之后才改成 "live"
});
```

官网的 `script.js` 会读取它，并处理页面上所有带 `data-app-link` 的元素（顶部导航按钮与页脚入口各一处）：

- `appStatus === "live"` 且 `appUrl` 非空：入口指向 `appUrl`，新标签页打开（`target="_blank"` 且 `rel="noopener noreferrer"`），文案变为 `appLabel`；
- 否则：入口回退到页面锚点 `#capture`，文案显示 `appLabel`（默认「应用即将到来」）。

也就是说：**在应用真正可访问之前，官网不会出现指向空地址的假按钮** —— 只要让 `appStatus` 保持 `"coming-soon"` 即可。

### 2. 应用 → 官网：构建变量 `VITE_OFFICIAL_SITE_URL`

应用的设置页提供「关于念头盒」入口（链接文案「打开官网首页」）指回官网。地址**在构建时注入**，不写死在源码里：

```bash
# Windows PowerShell
$env:BASE_PATH="/niantou-box/app/"; $env:VITE_OFFICIAL_SITE_URL="https://<你的用户名>.github.io/niantou-box/"; pnpm build

# macOS / Linux
BASE_PATH=/niantou-box/app/ VITE_OFFICIAL_SITE_URL=https://<你的用户名>.github.io/niantou-box/ pnpm build
```

- 只接受 `http` / `https` 绝对地址，并自动补齐结尾 `/`；空串、纯空白、相对路径（如 `/niantou-box/`）、裸域名（如 `niantou-box`）、`javascript:` 这类伪协议都会被当作「未配置」忽略。
- 未注入（或地址非法）时，设置页**不渲染**「关于念头盒」整块 —— 不会出现点不动的假链接。

**本仓库自带的工作流已经帮你注入好了**：`.github/workflows/deploy.yml` 里有一个 `OFFICIAL_SITE_URL`（默认 `https://chenzhe223-tech.github.io/niantou-box/`），构建时会作为 `VITE_OFFICIAL_SITE_URL` 传进去；构建后还会检查产物里有没有这个地址（没有则打一条 `::warning::`）。

- 官网换地址 → 改工作流里的 `OFFICIAL_SITE_URL`；
- 想在不改代码的前提下覆盖 → 在**应用仓库**的 `Settings → Secrets and variables → Actions → Variables` 里新建变量 `OFFICIAL_SITE_URL`，它会优先于默认值；
- 明确不想显示这个入口 → 把它设为空串。

### 3. 对接自检：`pnpm verify:site`

`scripts/verify-site-integration.mjs` 会加载官网**真实的 `script.js`** 在 jsdom 中执行，断言上述契约（入口点数量、`href`、`target`、`rel`、文案），并同时探测线上状态（官网首页、应用入口是否已部署、资源是否可取回、应用 bundle 是否注入了官网地址）。**未部署的应用只记为「待完成」，不算失败。**

### 4. 两种部署形态

- **同仓库、同站点（推荐）**：官网在站点根目录，应用源码放在 `app/` 子目录，一次部署同时上线两者（官网在 `/`，应用在 `/app/`）。对应工作流见交付物 `deploy.yml`（放置为 `.github/workflows/deploy.yml`）。
- **各自独立部署**：官网与应用分属两个仓库、两个地址。此时应用侧照常用 `VITE_OFFICIAL_SITE_URL` 指回官网，官网侧只把 `app-config.js` 的 `appUrl` 改成应用的真实地址即可，**应用代码一行都不用改**。
  具体做法：把本仓库的内容（`package.json` 在仓库根目录，即「仓库根 = 应用根」）推到一个**新仓库**，用本仓库自带的 `.github/workflows/deploy.yml` 发布；官网侧只需改 `app-config.js` 里的 `appUrl`。这一套交付物里已经备好：应用仓库压缩包 `nianbox-app-repo.zip`、官网侧配置 `app-config.方案B.js`、逐步说明 `方案B-应用独立部署-念头盒NianBox.md`。

> 小结：换用户名、换仓库名、把应用单独部署到另一个仓库，都**不需要改动应用源代码**；需要跟着改的只有官网侧的 `app-config.js` 与构建命令里的环境变量。

### 5. 运营数据与反馈后端（可选）：`VITE_TELEMETRY_*`

匿名统计与意见反馈的接收端同样**不写死在源码里**，全部在构建时注入。四个变量都可以不填，
不填时应用**不会发出任何网络请求**（设置页会如实显示「没有配置统计服务」）：

| 变量 | 作用 | 是否必需 |
| --- | --- | --- |
| `VITE_TELEMETRY_ENDPOINT` | 接收事件的接口地址（POST，`http`/`https` 绝对地址） | 接入时才需要 |
| `VITE_TELEMETRY_KEY` | **只能写入、不能读取**的令牌（如 Supabase anon key、自建 Worker 的写入令牌） | 后端要求时 |
| `VITE_APP_VERSION` | 应用版本号（CI 里用 Git 短 SHA），用于区分用户实际运行的是哪一版 | 建议填 |
| `VITE_DEV_DASHBOARD` | 设为 `1` / `true` / `on` 时，设置页会出现「打开开发者看板」入口 | 只有你自己需要时 |

```bash
# 例：接入自建后端并打开开发者看板入口
VITE_TELEMETRY_ENDPOINT=https://<后端地址>/ingest \
VITE_TELEMETRY_KEY=<只写令牌> \
VITE_APP_VERSION=$(git rev-parse HEAD) \
VITE_DEV_DASHBOARD=1 pnpm build
```

**安全前提（不可颠倒）**：前端产物里的令牌必须只能写入。读取运营数据的凭据只放在你自己的电脑
或后端的服务端环境里，永远不进前端产物；因此别人拿到应用网址也读不到任何数据。
接口需要能接受跨域 POST（返回 `Access-Control-Allow-Origin`，并允许 `X-NianBox-Key` 请求头）。

本仓库的 `.github/workflows/deploy.yml` 已经预留了这四个变量（全部取自仓库
`Settings → Secrets and variables → Actions → Variables`），留空即等于「不接入」，
因此现在直接推送是安全的。具体建表 SQL、周报查询与逐步接入步骤见交付文档
《运营数据与用户反馈-接入指南》。

## 十一、数据本地保存的特点

- 所有念头与项目保存在**当前设备、当前浏览器**的 IndexedDB 数据库中（库名 `nianbox`）。
- 不登录也能用：本地写入是第一站，写下就落库，界面立刻反馈。不写公开仓库里的 JSON 或静态文件。
- 没有注入 `VITE_CLOUD_ENDPOINT` 时**不发任何业务网络请求**；注入了云端地址时，只有在你登录之后，
  内容才会同步到**你自己的云端账号**（服务端按登录令牌校验归属），否则仍然只在本机。
- 作品（图片）与念头不同：作品**只保存在本机**，不进云端同步、不上传、不自动公开。
- 因此：
  - 清理浏览器数据、使用隐私/无痕模式、卸载浏览器、重置系统，都会造成数据丢失；
  - 未登录 / 未接入云端时，换设备、换浏览器看不到原来的记录；
  - 不同浏览器（Chrome / Safari / Edge）之间各自独立。
- 想跨终端用同一份数据，两条路：**登录云端账号**（同一账户跨终端同步），或**导出 → 传输 → 导入**。
- 设置页也明确写明了这段话：「当前版本采用本地存储，记录保存在这台设备的当前浏览器中。清理浏览器数据或更换设备前，请先导出备份。」

## 十二、如何导出与恢复数据

### 导出

**设置 → 备份与恢复 → 导出数据**，会下载一个 JSON 文件：

```
nianbox-backup-YYYY-MM-DD.json
```

文件包含格式标识、格式版本号（当前为 **v2**）、导出时间、应用版本、数量统计，以及：

- **全部念头与创意项目**（含回收站中的记录）与它们的关联信息、时间戳和状态字段；
- **全部本机作品**：作品元数据（关联念头、类型、生成方式、风格、比例、标题、创建时间）、
  **图片数据本体**，以及作品与念头之间的关联。

图片只写进这个 JSON 文件，**不会因为导出或导入而上传到云端**。备份体积会随作品数量和图片大小明显变大
（图片以 Base64 存在 JSON 里），导出与导入都会显示可读的进度、数量与体积提示，不会静默失败。

### 导入（恢复）

**设置 → 备份与恢复 → 导入数据**，选择之前导出的 JSON 文件：

1. 先做校验：文件格式、数据结构、必填字段、日期字段、记录 ID、状态与分类的合法值；备份为 v2 时还会校验
   作品元数据、图片格式与体积上限、以及作品与念头的关联；**校验不通过不会改动任何现有数据**；
2. 弹出确认框，显示备份的导出时间、版本、记录数量（念头 / 项目 / 作品 / 图片），以及**与本机重复的 ID 数量**；
3. 选择重复记录的处理方式（对念头、项目、作品同时生效）：
   - 保留现有数据，跳过相同 ID（默认，推荐）；
   - 用备份中的记录覆盖相同 ID；
   - 把相同 ID 的记录作为新记录导入（生成新 ID，不覆盖也不丢弃）；
4. 导入完成后给出结果统计（念头、项目、作品、恢复的图片张数）；若有单条记录的警告
   （例如项目关联的念头缺失、作品的关联念头不存在），会列在设置页中。

**重复 ID 与作品关联的映射**：作品的 `ideaId` 一定跟着它关联的念头一起变化——选择「跳过」时，
作品会挂到本机已存在的那条念头上；选择「作为新记录导入」时会为念头生成新 ID，并让作品指向这个新念头，
**不会把作品错连到另一条念头**。

**版本兼容**：v1 旧备份（只有念头与项目、没有作品字段）仍可正常导入，按「空作品集」处理。
v2 备份若含**关联念头不存在**的作品，会**跳过该作品并给出警告**（不会伪造关联）。

导入**不会**先清空现有数据。若要彻底重来，请先导出备份，再使用「清空全部数据」。
**所有写入在同一个 IndexedDB 事务里完成**（念头、项目、作品、图片一起提交），一次导入要么全部成功、
要么完全不动，不会出现「显示成功但只导入了一半」的情况。

> 建议：任何一次清理浏览器数据、更换设备或升级系统之前，先导出一份备份。

## 十三、跨设备同步：默认本地，接入云端后可选开启

**同步是可选能力，由构建时注入的 `VITE_CLOUD_ENDPOINT` 决定**，所以先说清楚两种形态：

| | 没注入云端地址 | 注入了云端地址（本仓库线上构建） |
| --- | --- | --- |
| 记录在哪 | 只在这台设备的这个浏览器里 | 本机 + 你自己的云端账号各一份 |
| 跨终端 | 靠「导出 → 传输 → 导入」手动合并 | 同一账户登录后自动同步（桌面浏览器 / iOS Safari / PWA / 微信内置浏览器） |
| 网络请求 | 不发业务请求 | 登录后由本机的 `outbox` 队列推送变更 |

同步的实现与边界（不是「把本地库整个传上去」）：

1. **本地写入优先**：先写本机 IndexedDB 并立刻反馈界面，再把变更放进队列推送。断网、服务端故障、令牌过期都不会丢掉刚写下的内容 —— 记录还在本机，恢复后补发。
2. **服务端逐条校验归属**：每条记录都带用户 ID，读和写都按当前登录用户过滤（`server/cloud-worker.test.mjs` 里有未授权一律拒绝的用例）。
3. **收件箱会区分状态**：明确标出「已同步」与「只在本机」，不会把还没上传的记录说成已备份。
4. **保存失败如实报错并保留输入**，不会出现「看着成功了、其实什么都没存」。
5. **旧设备数据迁移**：先在设置页「导出数据」拿到 JSON 备份，登录后导入即可；导入按 ID 去重，**不会清空**现有数据。
6. **密码找回依赖服务端邮件服务**；邮件服务没配置时，`#/cloud` 页不会出现「已发送邮件」这类说法。

如果你在多台设备上但不想登录，仍然只有「导出 → 传输文件 → 导入」这一条路；导入按 ID 去重，同一台设备之外新产生的内容会作为新记录导入，不做字段级合并。

> 服务端（Cloudflare Workers + D1）与 Worker Secret 的部署方式不在本仓库的日常开发流程里；没配好时应用会如实显示「这个构建没有配置云端地址」，不会假装同步过。

## 十四、已知限制与后续规划

### 已知限制

1. **跨设备同步默认关闭，且需要自建后端**：不注入 `VITE_CLOUD_ENDPOINT` 时应用完全本地；注入后要能注册 / 登录，还得服务端（Workers + D1）真的部署好。缺任何一环，界面都会如实说明，而不是给一个点了没反应的登录按钮。
2. **AI 分类与生图是可选能力**：未登录、未配置密钥或服务端没部署时用不了。这时不会假装成功，也不会用静态假图片顶替 —— 页面会给出「本机制作的念头卡片」这条路，并明确标注它不是 AI 生成。
3. **作品只在本机**：`works` / `workImages` 不参与云端同步，换设备看不到（这是隐私上的有意选择，不是缺陷）。
4. **没有社区功能**：本轮**没有**实现关注、私信、点赞、评论、公共作品流。分享是「把图片交到你手上（下载 / 系统分享）」，不是发布到某个公共页面。
5. **邮件发送取决于服务端是否配置**：没配置时退化为 `mailto:` 预填，由你在自己的邮件应用里确认后发送，界面不会说成「已发送」。
6. **数据丢失风险**：本地部分的数据生命周期跟随浏览器；清空浏览器数据即丢失（登录云端后的内容还有服务端一份，未登录时备份是唯一的保险）。
7. **Service Worker 只在生产构建注册**：开发环境不注册 SW，避免缓存干扰调试。
8. **离线能力有边界**：仅保证「已经缓存过的应用界面 + 已有本地数据」可用；第一次访问必须联网。应用界面使用网络优先策略，保证在线时不会卡在旧版本。
9. **PWA 安装方式因浏览器而异**：桌面 Chrome/Edge 有安装入口，iOS Safari 需要用「添加到主屏幕」，部分浏览器不提供安装能力。应用不会做无意义的自定义安装弹窗。
10. **未做真机验证**：本项目在受限环境中开发，浏览器自动化工具（如 Playwright）不可用，因此**没有进行真实 iOS / Android 设备或真实浏览器视口的验证**。响应式布局、安全区域、软键盘行为等只经过代码层面的设计与静态检查（详见第十五节），请以真机实测结果为准。系统分享与「保存到相册」在真机上的行为同样未验证。
11. **暂无导入导出以外的数据迁移手段**：没有 CSV 或 Markdown 导出。

### 后续规划（未实现，仅作为方向）

- 创意项目与 GitHub 仓库的联动（同步 issues、展示进度）；
- 端到端加密同步（目前为「登录令牌 + 服务端归属校验」，服务端能看到明文）；
- 用 AI 把零散念头聚成一个项目草案（聚类 / 补全）—— 需要用户明确授权与隐私方案；
- 更丰富的数据出口（Markdown / CSV）；
- 真实浏览器端到端测试（Playwright）接入 CI。

> README 只描述已经实现的功能，未实现的能力一律列在本节，不会写成"即将推出"的按钮。

## 十六、常见问题

**Q：直接双击 `dist/index.html` 打开可以吗？**
不建议。PWA 的 Manifest 与 Service Worker 需要 HTTP(S) 环境，而且 `file://` 下的 IndexedDB 行为在不同浏览器里并不一致。请用 `pnpm preview` 或任意静态服务器访问。

**Q：数据存在哪里？能直接看到吗？**
存在浏览器的 IndexedDB（库名 `nianbox`，当前版本为 v4，包含 `ideas` / `projects` / `meta` / `feedback` / `outbox` / `works` / `workImages` 七个对象仓库：前两个存念头与项目，`meta` 存本机设置，`feedback` 存本机反馈，`outbox` 存待同步的变更，最后两个分别存作品元数据与作品图片）。开发者工具的 Application → IndexedDB 可以看到。想稳妥地备份，请使用设置页的「导出数据」。

**Q：为什么不默认把数据同步到云端？**
因为「默认本地」才是对隐私最保守的选择：不登录、不收集就完全可用，公开的只是应用代码。跨终端同步是**你主动开启**的能力 —— 在设置里注册 / 登录自己的云端账号之后才发生，而不是在后台悄悄上传。没注入云端地址的构建根本不会发出业务请求。

**Q：本机卡片和 AI 生图都能做图，我该用哪个？**
只想马上把念头变成一张能发的图，用**本机制作的念头卡片**：不用登录、不发网络请求、不消耗额度，图上的文字就是你确认过的原文。想要更好看的视觉表达、并且愿意把**抽象后的主题词**（不含原文）交给服务端的图像模型，再用 **AI 增强生图**。界面上两者的标注不同，不会把本机卡片说成 AI 画的。

**Q：`pnpm build` 报 `spawn EPERM` 怎么办？**
确认脚本里带了 `--configLoader native`，并且 Node 版本 ≥ 22.18。详见第四节的说明。

**Q：官网和应用是什么关系？我该改哪里？**
官网是介绍页，应用是本体，可以放同一个站点（官网在根、应用在 `/app/`），也可以各自独立部署，两者只通过一条约定对接。规则、构建变量与自检命令见第十节。一句话：**应用源码不用改**，只需改官网侧的 `app-config.js`，以及构建时注入的 `VITE_OFFICIAL_SITE_URL`。

**Q：为什么设置页有时看不到「打开官网首页」这个入口？**
因为该入口只在构建时注入了合法的 `VITE_OFFICIAL_SITE_URL`（http/https 绝对地址）才会出现。没有注入时不渲染，避免出现点不动的假链接——这是刻意行为，不是 bug。
